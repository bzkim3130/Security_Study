# XSS/SQL Injection 대비 특수문자 필터링

## 한줄 요약
> XSS는 HTML/스크립트 구조를 깨는 문자(<, >)를, SQLi는 쿼리 구조를 깨는 문자('와 ;)를 노리며, 특수문자 필터링은 보조수단일 뿐 근본 대책은 Prepared Statement(SQLi)와 출력 인코딩(XSS)이다.

## 1. 특수문자별 위험성

| 문자 | 명칭 | 주로 악용되는 공격 | 이유 |
|---|---|---|---|
| `<` `>` | 꺾쇠괄호 | XSS | `<script>` 태그 삽입 |
| `'` | 작은따옴표 | SQLi | 문자열 리터럴 종료 → 쿼리 구조 조작 |
| `"` | 큰따옴표 | SQLi, XSS | 속성값/문자열 종료 |
| `;` | 세미콜론 | SQLi | 쿼리 종료 후 새 쿼리 삽입(Stacked Query) |
| `--` | 주석 처리 | SQLi | 뒤 구문 무력화(인증우회) |
| `/* */` | 블록주석 | SQLi | 구문 일부 무효화 |
| `=` | 등호 | SQLi | `OR 1=1` 항상 참 조건 |
| `%` | 퍼센트 | SQLi(LIKE구문) | 와일드카드 오남용 |
| `&` `&&` | 앰퍼샌드 | XSS, Command Injection | 엔티티/명령어 연결 |
| `\|` `\|\|` | 파이프 | Command Injection, SQLi | 명령 체이닝, 문자열 concat |
| `\` | 역슬래시 | SQLi | 이스케이프 문자 무력화 |
| script, javascript:, on이벤트 | 문자열 패턴 | XSS | 이벤트 핸들러 기반 실행 |

## 2. 공격 흐름

```
[XSS]
<script>alert(1)</script>  →  필터링 안 하면 브라우저에서 그대로 실행
     ↑
   < > 를 &lt; &gt; 로 치환하면 텍스트로만 표시(무력화)

[SQLi]
' OR '1'='1  →  WHERE id='' OR '1'='1'  (항상 참 → 로그인 우회)
     ↑
   ' 를 이스케이프(\') 하거나 Prepared Statement 쓰면 무력화
```

## 3. 방어 방식 비교

| 방식 | 원리 | 한계 |
|---|---|---|
| 필터링(Blacklist) | 특수문자 자체를 차단/제거 | 우회기법 많음(대소문자, 인코딩 우회) |
| 이스케이프/인코딩 | 문자를 안전한 형태로 변환 | 필터링보다 안전, 하지만 누락 위험 |
| Prepared Statement | 쿼리와 데이터를 분리 | **SQLi 근본 대책** (시험 정답) |
| 출력 인코딩(Output Encoding) | 출력 시점에 HTML 이스케이프 | **XSS의 확실한 대책** |

## 암기 팁
- **"꺾쌍쿼세따"**: **꺾**쇠(`<>`) **쌍**따옴표(`"`) → XSS 담당 / **쿼**트(`'`) **세**미콜론(`;`) **따**옴표 → SQLi 담당
- **"SQL은 문장을 끊고(`;` `--`) 문자열을 깨고(`'`), XSS는 태그를 열고 닫는다(`<` `>`)"**

## 헷갈리는 포인트
- **"특수문자 필터링만 하면 SQLi 완벽 차단"** → **틀림**, 근본 대책은 **Prepared Statement(바인드 변수)**
- **XSS는 입력 필터링보다 출력 시점 인코딩(Output Encoding)이 더 확실한 대책**
- 필터링(Blacklist) 방식은 대소문자변형, 인코딩우회(%3Cscript%3E 등) 등으로 쉽게 우회됨

## 관련 기출/문제
- XSS/SQLi 각각 악용되는 특수문자 구분
- SQLi 근본 대책(Prepared Statement) vs 보조 대책(필터링) 구분
- XSS 방어의 핵심(출력 인코딩)
