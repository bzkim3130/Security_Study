# AWS IAM (Identity and Access Management)

## 한줄 요약
> IAM은 User/Group/Role/Policy로 권한을 관리하는 AWS의 전역(리전 무관) 서비스이며, 정책 평가 시 명시적 거부(Explicit Deny)가 항상 최우선 적용된다.

## 1. 핵심 구성요소

| 구성요소 | 역할 |
|---|---|
| User | 개별 사용자(장기 자격증명 보유 가능) |
| Group | 사용자들을 묶어 정책을 일괄 적용 |
| Role | 임시 자격증명을 부여받는 "신원"(사람이 아닌 서비스/타 계정도 맡을 수 있음) |
| Policy | 권한을 정의하는 JSON 문서(허용/거부 규칙) |
| Root User | 계정 생성 시 최초 계정, 모든 권한 보유(평소 사용 지양) |
| MFA | 다중 인증(추가 보안계층) |
| ARN (Amazon Resource Name) | AWS 리소스를 고유하게 식별하는 이름 형식 |

## 2. 관계도

```
Group ──(정책 부여)──▶ 여러 User에 일괄 적용
User  ──(정책 직접 부여)──▶ 개별 권한
Role  ──(AssumeRole)──▶ 임시 자격증명 획득(사람/서비스/타계정이 "맡아 쓰는" 신원)
Policy ──(JSON 문서)──▶ User/Group/Role에 연결되어 실제 권한 정의
```

## 3. User(장기자격증명) vs Role(임시자격증명)

| 구분 | User | Role |
|---|---|---|
| 자격증명 | 장기(Access Key 등, 직접 발급) | **임시**(AssumeRole로 획득, 자동 만료) |
| 용도 | 사람이 직접 로그인/API 사용 | EC2, Lambda 등 서비스가 "맡아 쓰는" 권한, 교차계정 접근 |
| 보안권장 | 최소화(가능하면 Role 사용 권장) | AWS 권장 방식 |

## 4. 정책 평가 순서 (핵심 함정)

```
평가 우선순위: 명시적 거부(Explicit Deny) > 명시적 허용(Explicit Allow) > 암묵적 거부(Implicit Deny, 기본값)
```
→ 어떤 정책에서든 **한 번이라도 Deny가 명시**되면, 다른 곳에서 Allow가 있어도 **무조건 거부**

## 5. IAM의 전역(Global) 특성

- IAM은 **리전(Region)에 종속되지 않는 전역 서비스** — 특정 리전에서 만든 IAM 사용자가 모든 리전에서 동일하게 적용됨 (EC2, S3 버킷 등 대부분 서비스와 다른 특성)

## 6. 포렌식/보안 관점

- **AssumeRole 오남용**: 공격자가 낮은 권한 계정으로 침투 후 Role을 탈취/악용해 권한 상승(Privilege Escalation)을 시도하는 경우가 흔함
- **CloudTrail 로그 분석**: 누가 언제 어떤 Role을 Assume했는지, 어떤 API를 호출했는지 기록 → 침해사고 조사의 핵심 증거

## 암기 팁
- **"유그롤폴"**: **유**저-**그**룹-**롤**-**폴**리시 4대 구성요소
- **"Role은 잠깐 빌려쓰는 옷, User는 내 옷"** — 임시 vs 장기 자격증명
- **"Deny가 뜨면 무조건 진다"** — 정책 평가 시 Explicit Deny 최우선

## 헷갈리는 포인트
- IAM이 리전별로 따로 관리된다고 착각하기 쉬움 — **IAM은 전역 서비스**
- Role은 "그룹의 하위개념"이 아니라 **완전히 별개의 개념**(임시 자격증명 메커니즘)
- 명시적 허용이 여러 곳에 있어도 **단 하나의 명시적 거부**가 있으면 최종 결과는 거부

## 관련 기출/문제
- IAM 4대 구성요소(User/Group/Role/Policy) 역할 구분
- 정책 평가 우선순위(Explicit Deny 최우선)
- IAM의 전역 서비스 특성
- User vs Role의 자격증명 차이(장기 vs 임시)
