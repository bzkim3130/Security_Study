# DB 암호화 방식 비교 (API / Plug-in / TDE / Hybrid)

## 한줄 요약
> DB 암호화는 "어디서 암복호화 로직이 동작하느냐"에 따라 API(응용서버)-Plugin(DB서버)-TDE(DBMS엔진 자체)-Hybrid(혼합) 4가지로 나뉘며, TDE가 가장 투명하고(애플리케이션 수정 불필요) API가 가장 유연하지만 구현 부담이 크다.

## 1. 4가지 방식 비교

| 방식 | 암복호화 위치 | 애플리케이션 수정 | 장점 | 단점 |
|---|---|---|---|---|
| API 방식 | 응용서버(애플리케이션 레벨) | 필요(암복호화 함수 호출 코드 삽입) | 세밀한 제어, DB 종류 무관 | 개발 부담 큼, 소스코드 전반 수정 필요 |
| Plug-in 방식 | DB 서버(DBMS에 플러그인 설치) | 불필요(트리거/플러그인이 처리) | 애플리케이션 수정 최소화 | DB 서버 부하 증가, DBMS 종속적 |
| TDE (Transparent Data Encryption) | DBMS 엔진 자체(내장 기능) | **완전 불필요**(투명) | 적용 가장 쉬움, 성능 최적화됨(엔진 내장) | 세밀한 컬럼별 정책 제한적, DBMS 라이선스 필요한 경우 많음 |
| Hybrid 방식 | API + Plug-in 혼합 | 일부 필요 | 상황별 유연한 적용 | 구조 복잡, 관리 포인트 증가 |

## 2. 도식화

```
[API 방식]
애플리케이션 ──(암호화 함수 직접 호출)──▶ DB (평문 저장 안 함, 암호문만 저장)

[Plug-in 방식]
애플리케이션 ──(평문 SQL 그대로)──▶ DB서버(플러그인이 중간에서 암복호화) ──▶ 저장소

[TDE 방식]
애플리케이션 ──(평문 SQL 그대로)──▶ DBMS엔진(디스크 저장 시 자동 암호화) ──▶ 저장소
                                     ↑ 애플리케이션은 이 과정을 전혀 모름(투명)

[Hybrid]
민감컬럼: API로 개별 암호화 + 나머지: Plug-in/TDE로 일괄 암호화
```

## 3. 선택 기준

- **세밀한 컬럼별 접근제어가 중요**: API 방식
- **레거시 시스템, 애플리케이션 수정이 어려움**: TDE 또는 Plug-in
- **디스크 도난/물리적 유출 방지가 목적(저장 데이터 암호화)**: TDE로 충분
- **특정 컬럼만 별도 강력 보호 + 나머지는 일괄 보호**: Hybrid

## 암기 팁
- **"API=코드로 직접, Plugin=DB서버가 중간에서, TDE=엔진이 알아서(투명), Hybrid=섞어쓰기"**
- **TDE의 "Transparent(투명)" = 애플리케이션이 암호화 여부를 전혀 몰라도 됨**이 핵심 특징
- 개발부담 순서: **"API(제일 힘듦) > Plugin > TDE(제일 편함)"**

## 헷갈리는 포인트
- TDE는 "전송 중 암호화"가 아니라 **저장 시(at rest) 암호화**가 핵심 — 네트워크 전송 구간 보호는 별도(TLS 등)로 필요
- Plug-in 방식은 애플리케이션 수정은 적지만 **DB 서버 자체의 부하가 늘어남** — "수정 없음=부담 없음"이 아님
- API 방식이 가장 세밀하지만 **모든 애플리케이션 코드를 다 고쳐야 하는 큰 부담**이 따름

## 관련 기출/문제
- 4가지 방식별 암복호화 수행 위치 구분
- TDE의 "투명성"이 의미하는 것
- 방식별 장단점 매칭
