# S/MIME (Secure/Multipurpose Internet Mail Extensions)

## 한줄 요약
> S/MIME은 대칭키(메시지 암호화, 빠름)+비대칭키(대칭키 자체를 암호화, 키교환용)로 이메일 기밀성을, 전자서명(X.509 인증서 기반)으로 인증·무결성·부인방지를 제공하는 하이브리드 방식이다.

## 1. 핵심 메커니즘

| 기능 | 사용 기술 |
|---|---|
| 기밀성 | 대칭키로 메시지 암호화 + 그 대칭키를 수신자의 공개키로 암호화(봉투) |
| 인증/무결성/부인방지 | 발신자의 개인키로 전자서명 |
| 인증서 | X.509 v3 인증서(PKI 기반) |

## 2. 동작 흐름

```
[발신자]
1. 대칭키(세션키) 생성
2. 메시지를 대칭키로 암호화 (빠름)
3. 대칭키를 수신자의 공개키로 암호화 (전자봉투)
4. 메시지 해시를 발신자 개인키로 서명

[수신자]
5. 발신자 공개키로 서명 검증
6. 자신의 개인키로 대칭키 복호화
7. 그 대칭키로 메시지 복호화
```

## 3. S/MIME 데이터 타입 비교

| 타입 | 인코딩 범위 | 특징 |
|---|---|---|
| Signed Data | 내용+서명 전체를 base64 인코딩 | 서명 검증까지 완전 지원 |
| **Clear-signed Data** | **내용은 인코딩 안 함**(평문 그대로 읽힘), 서명만 별도 첨부 | 비S/MIME 클라이언트도 **내용은** 읽을 수 있음, 단 **서명 검증은 S/MIME 지원 클라이언트만 가능** |
| Enveloped Data | 암호화된 데이터 | 기밀성 제공, 수신자만 복호화 가능 |

**핵심 함정**: "Clear-signed data는 비S/MIME 사용자도 서명까지 검증 가능하다" → **틀림**. 내용은 읽을 수 있지만(인코딩 안 됐으므로), **서명 검증에는 여전히 S/MIME 지원이 필요**

## 4. 대칭키+비대칭키를 함께 쓰는 이유

```
대칭키만 쓰면: 빠르지만 키를 어떻게 안전하게 전달할지 문제
비대칭키만 쓰면: 키 전달은 안전하지만 대용량 메시지 암호화엔 너무 느림
    │
    ▼
하이브리드: 메시지는 대칭키(빠름)로, 그 대칭키는 비대칭키(안전)로 감싸서 전달
```

## 암기 팁
- **"대메-비키"**: **대**칭키로 **메**시지, **비**대칭키로 **키**(대칭키 자체) — 무엇을 무엇으로 암호화하는지 순서
- **"클서-내봄, 검못"**: **클**리어사인드(**서**명타입)는 **내**용은 **봄**(읽힘), 하지만 검증은 **못**함(비S/MIME 클라이언트는)
- 서명=개인키(나만 가능), 봉투=공개키(상대만 열람)라는 기존 전자서명 원리와 동일 구조

## 헷갈리는 포인트
- Clear-signed data에서 "내용을 읽을 수 있다"는 것과 "서명을 검증할 수 있다"는 것은 **별개** — 시험 함정 포인트
- S/MIME의 인증서는 X.509 v3 기반이며, PKI 인프라(CA)가 전제되어야 동작

## 관련 기출/문제
- S/MIME 데이터 타입(Signed/Clear-signed/Enveloped)별 특징 구분
- Clear-signed data에서 비S/MIME 사용자가 할 수 있는 것과 없는 것
- 대칭키+비대칭키 하이브리드 사용 이유
